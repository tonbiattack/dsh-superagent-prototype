# 012 Issue自動実装の使い方

このドキュメントは、GitHub Issue に `autopilot` ラベルを付けるだけで、dsh-superagent が自動で実装し、検証し、PR を作成してマージするまでの使い方を日本語で説明します。

対象は「実際に運用する人」です。設計の背景は [009 Issue autopilot](009-issue-autopilot-fork.md)、全体構成は [007 Architecture](007-architecture.md)、導入は [006 Deployment](006-deployment.md) を参照してください。

## 全体の流れ

```
① Issue にラベルを付ける
        ↓
② ポーリングが検知してキューに積む（既定60秒間隔）
        ↓
③ スケジューラがジョブを開始（同時実行数の範囲内）
        ↓
④ エージェントが専用ブランチ・専用ディレクトリで実装
        ↓
⑤ dsh-superagent 自身が検証コマンドを実行
        ↓
⑥ 合格したら push → PR 作成 → 条件を満たせばマージ
        ↓
⑦ パネルの「自動実装」タブで結果を確認
```

**重要:** ②〜⑦ はすべて自動です。人が操作するのは ① のラベル付けと、⑦ の結果確認、そして止めたいときの操作だけです。

## 前提条件

以下がすべて済んでいる必要があります。未完了だと何も動きません。

| 前提 | 確認方法 |
| --- | --- |
| セットアップ完了（GitHub アカウント・リポジトリ・CLI） | パネルの「概要」に問題が出ていないこと |
| GitHub の許可リストに、Issue を書く人・ラベルを付ける人が入っている | 「設定 → 評価 → 各ソース」の GitHub 許可リスト |
| 監視対象リポジトリのローカルチェックアウトがある | 下記「リポジトリの登録」参照 |
| 検証コマンドが決まっている | 例: `pnpm check`、`npm test` |

## リポジトリの登録

「設定 → 自動実装」で設定します。**この設定はパネルからのみ変更できます**（エージェントのツールからは変更不可）。

### 監視するリポジトリ

1行に1リポジトリ、`owner/name` の後ろに空白区切りで**ローカルの絶対パス**を書きます。

```
tonbiattack/my-app /home/me/src/my-app
tonbiattack/another-repo /home/me/src/another-repo
```

- パスは **WSL2 / Linux 側**の絶対パスです（`/mnt/c/...` は避けてください。理由は [011 Windows + WSL2](011-windows-wsl.md)）
- パスを省略すると、チケット用ディレクトリ配下に `owner-name` という名前で探します
- そのディレクトリは **対象リポジトリの git チェックアウトである必要があります**。`origin` が別リポジトリを指していると、誤ったリポジトリへの実装を防ぐため**ジョブは失敗します**

### 実行ラベル

既定は `autopilot` です。別名にしたい場合だけ変更します。**このラベルが自動実行の唯一のスイッチ**です。

### 検証コマンド（必須）

**これを空にすると自動実装は有効化できません。** dsh-superagent 自身がジョブのディレクトリで実行し、終了コード 0 のときだけ合格とします。

```
pnpm check
```

- エージェントが「完了しました」と報告しても、それは証拠として扱われません
- タイムアウト（既定1800秒）を超えると失敗扱いです
- 失敗した場合、PR は作られず、ジョブに理由が記録されます

### 同時実行数

| 設定 | 既定 | 意味 |
| --- | --- | --- |
| 同時実行の総数 | 1 | 全リポジトリ合計で同時に走るジョブ数（1〜16） |
| リポジトリごとの同時実行数 | 1 | 1リポジトリが占有できる枠（1〜16） |
| ポーリング間隔 | 60秒 | Issue を読みに行く間隔（30〜3600秒） |
| 最大試行回数 | 3 | 自動リトライの上限（1〜10） |

最初は既定の 1 のままを推奨します。動作に慣れてから増やしてください。

### 配信の設定

| 設定 | 既定 | 説明 |
| --- | --- | --- |
| PR を作成 | オン | 実装後に PR を作る |
| ブランチを push | オン | 普通の push のみ。force push はしません |
| 自動マージ | オン | 条件を満たしたときだけマージ |
| マージ方法 | squash | squash / merge commit / rebase |
| 必須チェックを待つ | オン | 必須チェックが未実行・失敗・実行中ならマージしない |
| ブランチ保護を守る | オン | 必要な承認数に足りなければマージしない |
| 既定ブランチへの直接コミットを禁止 | オン | 既定ブランチ名が何であっても拒否 |
| マージ後に Issue を閉じる | オフ | オンにすると PR 本文に `Closes #番号` を書く |
| Issue にコメント | オフ | 結果を Issue に残す |

**自動マージをオフにすると、PR を作るところで止まります。** まずはオフで試し、PR の内容を確認してからオンにする運用も安全です。

## 実際の使い方

### 1. Issue を書く

通常の Issue と同じです。タイトルと本文に、**何をしてほしいか**を書きます。

```markdown
タイトル: 設定画面の保存ボタンが二重送信される

本文:
設定画面で保存を素早く2回押すと、リクエストが2回飛びます。
1回だけ送られるようにしてください。
```

コツ:

- **1 Issue = 1 つの変更**にすると成功しやすくなります
- 対象ファイルや再現手順があると精度が上がります
- リポジトリに `AGENTS.md` や `README.md` があれば、エージェントが読みます

### 2. ラベルを付ける

`autopilot` ラベルを付けます。**これが実行指示になります。**

重要な制約:

- **ラベルを付けた人が許可リストにいる必要があります。** Issue の作者ではなく、**ラベルを付けた人**で判定します
- 第三者が他人の Issue にラベルを付けても実行されません
- ラベルの記録が取得できない場合も実行されません（安全側に倒します）

### 3. 待つ

既定60秒以内に検知され、キューに積まれます。同時実行数の枠が空いていれば開始します。

パネルの「自動実装」タブで状態を確認できます。

| 状態 | 意味 |
| --- | --- |
| 待機中（queued） | 検知済み。実行枠が空くのを待っている |
| 実行中（running） | エージェントが作業中 |
| 完了（done） | マージまで完了、またはチケットが正常終了 |
| 失敗（failed） | エラー。理由が表示される |
| スキップ（skipped） | 対象外（ラベルが外れた、Issue が閉じた等） |
| 一時停止（paused） | 人が止めた |

### 4. 結果を確認する

「完了」になったら、PR の URL とマージ SHA がジョブに記録されています。パネルから PR を開けます。

## 止めたいとき

「自動実装」タブのジョブごとのボタンで操作します。

| 操作 | 使える状態 | 効果 |
| --- | --- | --- |
| 一時停止 | 待機中 | 実行を止める。再開すると待機中に戻る |
| スキップ | 待機中・一時停止中 | その Issue を対象外にする（変更は残る） |
| 再試行 | 失敗・スキップ | 試行回数をリセットして待機中に戻す |

**実行中のジョブは一時停止・スキップできません。** エージェントが作業中のため、安全に止められないからです。止めたい場合は「実行」タブで該当チケットを停止してください。

### ラベルを外す

実行前に `autopilot` ラベルを外すと、次のポーリングでスキップされます。**これが最も確実な中止方法**です。

### 全体を止める

「設定 → 自動実装」で「自動実装を有効にする」をオフにします。新しいジョブは開始されなくなります（実行中のものは継続）。

## 何が起きたか分からないとき

### パネルで確認する

「自動実装」タブに、全ジョブと状態・エラー理由が並びます。ヘルス表示がエラーの場合は、ポーリング失敗かジョブ失敗の理由が出ます。

### よくある失敗と対処

| 表示 | 原因 | 対処 |
| --- | --- | --- |
| `the issue is no longer open or no longer carries the label` | 実行直前にラベルが外れた／Issue が閉じた | 意図した動作。必要なら再度ラベルを付ける |
| `... is a checkout of another repository, not ...` | チェックアウトの `origin` が別リポジトリ | 正しいリポジトリを clone し直し、設定のパスを直す |
| `... is not a Git checkout` | パスが git リポジトリでない | 正しいパスを設定する |
| `the autopilot label has no recorded author` | ラベル付与者の記録が取れない | 一度ラベルを外して付け直す |
| `... applied the autopilot label but may not originate work` | ラベルを付けた人が許可リストにいない | 許可リストに追加するか、許可された人に付け直してもらう |
| `Refusing to deliver: ...` | 検証コマンドが失敗した | エラー内容を確認。ローカルで同じコマンドを実行して再現する |
| `required checks failed: ...` | CI が落ちた | CI の失敗を直す。PR は開いたまま |
| `required checks are still running: ...` | CI が実行中 | 待つ。次のポーリングで再試行される |
| `required checks have not run: ...` | 必須チェックが一度も走っていない | ワークフローの設定を確認 |
| `the repository requires N approving review(s); it has M` | 承認が足りない | 承認する。次のポーリングで再試行される |
| `the pull request conflicts with its base branch` | コンフリクト | 手動で解消するか、Issue を閉じて作り直す |
| `GitHub reports the pull request as blocked` | GitHub 側のマージ条件を満たしていない | GitHub の PR 画面で理由を確認 |

## 安全のための設計（知っておくと安心）

この機能は「間違っても危険なことをしない」方向に倒してあります。

- **ラベルがなければ動かない。** ラベルは自動で付きません
- **許可された人がラベルを付けたときだけ動く。** Issue の作者だけでは不十分です
- **検証は dsh-superagent 自身が実行する。** エージェントの「できました」は信じません
- **既定ブランチへは直接コミットしない。** force push もしません
- **必須チェック・承認・コンフリクトを迂回しない。** 満たせないときは PR を開いたまま理由を残します
- **同じ Issue を二重に実行しない。** リポジトリの不変 ID + Issue 番号で管理し、プロセス間はロックで排他します
- **再起動しても作業を失わない。** 読めなかった状態を「無い」と誤解せず、判断を保留します
- **リポジトリを取り違えない。** チェックアウトの `origin` を確認してから実行します

## 制限事項

現時点で分かっている制限です。

- **ブランチ保護ありのリポジトリでの実マージは未検証。** 保護なしのリポジトリでは実マージを確認済みです。保護ありの経路は単体テストで網羅していますが、実環境での確認は残っています
- **1 Issue = 1 ブランチ**（`agent/issue-<番号>`）。同じ Issue で別の変更をしたい場合は、Issue を分けてください
- **実行中のジョブは人から止められません。** チケット停止を使ってください
- **検証コマンドは1つだけ。** 複数必要な場合は `pnpm check && pnpm lint` のようにまとめてください

## 設定の反映タイミング

| 変更 | 反映 |
| --- | --- |
| 監視リポジトリ・ラベル・検証コマンド | 次のポーリングから |
| 同時実行数・ポーリング間隔 | 次のポーリングから |
| 有効／無効 | 次のポーリングから（実行中は継続） |

設定を保存すると即座に1回ポーリングが走ります。
